# 왕복 횟수 실험 해석 (#6)

## 무엇을 쟀나
"토큰 절감"을 첫 답의 길이가 아니라 **위반 없는 코드가 나올 때까지 몇 번 다시 시켜야 하나**로 쟀다. 사용자가 모호하게 말하면 여러 번 되묻고 고치게 되는 비용이 진짜 비용이라는 피드백을 반영한 정의다.

- 코딩 역할: 새 Claude 서브에이전트. 이 프로젝트 맥락 없이 입력 파일 2개(지시문, 요청 또는 사양서)만 읽게 함. 수정 요청은 같은 에이전트에게 이어서 보냄 (실제 대화처럼)
- 점검: 서비스 6단계와 같은 함수(`reviewCode`, Gemini Flash-Lite). 기준 규칙은 두 조건 동일
- 수정 요청문: 서비스가 만드는 것과 같은 문장(`buildFixPrompt`)
- 회차별 코드·점검 결과·수정 요청문이 모두 이 폴더에 원본으로 있음 (`N-조건-rK.txt`, `-review.json`, `.prompt.md`)

## 결과

|---|---|---|---|---|---|

- 두 요청 모두 **사양서가 있으면 첫 답에서 위반 0**, 없으면 1~2번 더 시켜야 했다
- 대화 기준 토큰(매 회차 대화 전체를 다시 읽는다고 본 추정)은 사양서 쪽이 요청 1에서 약 71%, 요청 2에서 약 31% 적었다

## 정직하게 봐야 할 점
- **에이전트 보고 토큰은 요청 2에서 사양서 쪽이 오히려 조금 많았다.** 이 값은 서브에이전트가 끝날 때 보고한 수로, 파일 읽기 같은 도구 사용과 에이전트 자체 지시문이 포함되고, 이어서 일을 시킨 경우 앞 대화가 포함된 것으로 보인다. 사양서(약 6.5천 자)를 읽는 비용이 고정으로 붙기 때문에, 고칠 게 적은 요청에서는 차이가 줄거나 뒤집힐 수 있다. 실제 절감은 "왕복이 몇 번 줄었나"에서 나온다
- 요청 1 사양서 없음의 1회차에서 에이전트는 지적된 2개를 고쳤지만, 점검 모델이 0회차에 '문제없음'이라 했던 다른 2개(돈 기록, 권한 확인)를 새로 지적했다. 점검 모델이 회차마다 흔들린 것이다. 사양서는 이런 항목을 처음부터 요구사항으로 넣어서 이 흔들림을 피해갔다
- 요청 2건, 조건당 1회. 통계가 아니라 경향이다
- 처음에는 코딩 역할도 Gemini Flash로 하려 했으나 11/2 저녁 Flash가 1시간 넘게 과부하(503/429)여서 중단했고, "실제로는 Flash-Lite로 코딩하지 않는다"는 피드백에 따라 Claude 서브에이전트로 바꿨다. 이전 시도의 부분 결과는 쓰지 않았다

## 발표에서 쓸 말
"같은 요청을 Claude 코딩 에이전트에 그냥 넣으면 보안·구조 문제를 고쳐 달라고 1~2번 더 시켜야 했고, 사양서를 넣으면 첫 답에서 끝났다. 사양서를 읽는 비용은 있지만, 되묻고 고치는 왕복이 사라진다."

## 11/14 추가: 요청 3건을 더 돌림 (같은 절차)

| 요청 | 조건 | 회차별 위반 | 수정 요청 | 대화 기준 토큰(추정) |
|---|---|---|---|---|
| 3 중고 교재 게시판 | 사양서 없음 | 2 → 0 | 1회 | ≈16,571 |
| 3 중고 교재 게시판 | 사양서 있음 | 0 | 0회 | ≈9,860 |
| 4 헬스장 PT 예약 | 사양서 없음 | 3 → 1 → 1 → 0 | 3회 | ≈54,982 |
| 4 헬스장 PT 예약 | 사양서 있음 | 0 | 0회 | ≈8,676 |
| 5 과제 마감·역할 분담 | 사양서 없음 | 0 | 0회 | ≈3,336 |
| 5 과제 마감·역할 분담 | 사양서 있음 | 0 | 0회 | ≈12,384 |

- 5건을 합치면: **사양서가 있으면 5건 모두 첫 답에서 위반 0**. 사양서가 없으면 5건 중 4건에서 수정 요청이 1~3회 필요했다 (2·1·1·3·0회)
- **요청 5는 차이가 없었다.** 로그인도 돈도 없는 단순한 앱이라 사양서 없이도 첫 답이 깨끗했고, 사양서 쪽이 토큰만 더 썼다 (≈12,384 대 ≈3,336). 사양서의 이득은 권한·돈·기록 같은 규칙이 걸린 앱에서 나온다
- 요청 4의 3회 왕복 중 2회는 고친 뒤에 점검 모델이 새 항목(빈 catch, 파일 분리)을 지적한 것이다. 처음부터 다 짚지 못하는 점검 모델의 흔들림이 왕복을 늘렸다
- 요청 4의 마지막 수정 회차는 코딩 에이전트가 사용 한도에 걸려 한 번 끊겼다가 이어서 끝냈다 (usage.jsonl에 표시)
- 여전히 조건당 1회 실행이다. 통계가 아니라 경향이고, 점검도 AI라서 "위반 0"이 "결함 없음"을 뜻하지는 않는다
